# Convention responsibility

Each convention governs one recurring decision with identifiable conditions of application. Its title and trigger name that decision. Keep the rule, rationale, qualifying conditions, exceptions, and useful examples together. Split agreements that a plausible task can consult or change independently.

Before: a Testing convention requires fresh nested fixture state and fixed clocks. A mutation-leak fix needs only fixture independence; an expiry-test fix needs clock control. After: give each decision its own convention and trigger. Two sections under Testing would still load both for either task.

Conversely, keep canonical option spelling with the exception that retains a shipped spelling for supported callers until the next major version. Both determine whether an alias may exist. Splitting the exception into an unrelated compatibility file could cause the main rule to be applied incorrectly.

Refactoring preserves obligations, exceptions, and scope. Show complete proposed target files and a source-to-destination mapping before applying an unapproved structural plan. Reuse approval of a concrete plan. "Three attempts" versus "two attempts" for the same job is a policy conflict to resolve, not a wording choice to hide in a split. Do not infer responsibilities from file length, headings, broad technology names, or a target file count.
