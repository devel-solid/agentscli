# Mechanical validation

Read when defining checks, skill scripts, resource formats, or failure handling.

- Prefer deterministic validation whenever a rule is mechanical: schemas, required fields, duplicate keys, dependency identities, file ownership, paths, links, hashes, executable intent, role guards, and release identities. Apply this equally to the monorepo, consumer projects, and independent hub repositories.
- Keep agent-facing checks inside the skill responsible for the operation, with its complete custom support. Do not expand the public CLI for agent tasks or share skill implementations between environments. Each skill must state when to run its own checks and how to report failures.
- Treat validation as read-only preflight. Plan against complete prospective resources, including canonical package declarations on first apply and accepted source declarations for imported resources. Edited managed copies are drift to replace; they do not redefine authoritative dependencies. Invalid authoritative source or ambiguous unmanaged collisions block all planned writes.
- Parse YAML and Markdown structurally. Reject duplicate/unknown keys, aliases, invalid types, unsafe paths, and unsupported active syntax. Inspect inline, reference, image, and HTML links, normalized/encoded targets, fragments, queries, source/output aliases, and resource support ownership. Literal invalid examples are data; executable workflow examples cannot conceal foreign-resource paths.
- Convention checkers reject dependency declarations and active links to any other convention or skill. Skill checkers reject direct links and fixed foreign-resource workflow paths, while permitting their own dependency/support files and plain identity mentions. Root instruction discovery links remain permitted.
- Skill configuration checks require agreement between `metadata.agentscli` and the reserved sibling `agentscli-skill.yml`. Validate a mapping with optional skill-only `requires` references, strict fields/types, origins, duplicate identities, and full explicit selection. Reject obsolete declarations rather than reading or converting them. A convention with the same identity never satisfies a skill reference; convention selection is independent of dependency closure.
- Keep semantic review distinct. Scripts cannot prove that a convention is self-contained prose, a skill has one useful responsibility, or a release has compatible impact. Agents review those properties and choose impact; scripts compute and verify deterministic consequences.
- Make failures actionable and preserve evidence: identify the rejected field/path, candidate commit when applicable, and completed/pending effects. Use injected adapters for lightweight unit tests. Never execute downloaded skills, hooks, filters, or scripts to validate them.
- Keep preview/check write-free. Report actual checks and limitations; passing schema checks or unit tests does not establish a completed publication or absence of bugs.
