# Proposal

## Why

Reusing conventions and skills between projects currently requires manual copying and adaptation, as happened when moving skill-authoring guidance between SGO and agentscli. The product is ready to support explicitly selected shared resources through ordinary Git repositories, without a hosted registry or service to operate.

## What Changes

- Organize the repository as an npm-workspaces monorepo with independently installable and versioned `@devel-solid/agentscli` and `@devel-solid/agentscli-hub` packages. Preserve the existing `agentscli` executable and repository history. The new package starts at `0.1.0` with the `agentscli-hub-v0.1.0` tag pattern.
- **BREAKING:** Expose only `agentscli apply` and `agentscli-hub apply <directory>`, with help/version and write-free previews. Retire `init` without an alias; public consumer `validate`/`sync` remain removed. The build skill owns deterministic validation, rendering, planning, synchronization, and freshness checks; consumer apply reuses its packaged engine.
- Apply creates missing setup on first use and replaces managed resources on later use, removing obsolete managed files. Preserve authored content and project state in place; do not merge manual edits to managed files or require backup/delete/recreate of the project. Product skill trees are managed: four in consumers and five in hubs.
- Keep build-skill scripts usable with Node and versioned project files alone. Consumer apply refreshes packaged skills and regenerates managed documents/imported skill installations from local inputs; it preserves the accepted hub snapshot and never fetches or changes its pin implicitly.
- Hub apply creates a standalone Git project or refreshes its managed scaffold/skills, preserving authored instructions, internal/shared conventions, shared skills, content version, and Git metadata/policy. Its included authoring skills contain deterministic validation scripts.
- Include `agentscli-hub-publish` in every initialized hub. On a publication request, the agent assesses changes, selects the next content version without requiring user version selection, updates the hub manifest, validates, and commits/tags/pushes through native Git. Mechanical release checks and helpers ship inside this skill; no public release command is added.
- Maintain 12 independent operational skills with one responsibility each: three administrative skills under root `.agents/skills/`, four consumer sources under `packages/agentscli/assets/templates/skills/`, and five hub sources under `packages/agentscli-hub/assets/templates/skills/`. Even identical bodies have separate owned sources and maintenance; no operational skill is shared, wrapped, or generated from another environment's skill.
- Give the nine distributed operational skills `license: MIT`, exactly `compatibility: Requires Node.js >= 22.`, and string metadata `generatedBy`/`generatorVersion`. Each package stamps its own package name and real version during deterministic asset assembly; apply copies those prepared resources. Add no independent skill version stream or provenance stamp to the three administrative skills or imported hub resources.
- Remove `agentscli.yml` and its distribution/context contract during implementation. Package assembly discovers complete skill directories in each package's fixed asset subtree, and source-repository guards use existing package/workspace metadata. Do not introduce a replacement source manifest. Preserve the distinct `agentscli-hub.yml` content manifest and consumer `.agentscli/config.yml`.
- Keep tool and content versions separate: the hub CLI package starts at `0.1.0`, while each created hub's `agentscli-hub.yml` records its own content `version`, initially `1.0.0`. Content releases use that hub repository's `v<version>` tags independently of CLI releases; `schemaVersion` identifies file format only.
- Discover shareable convention templates under `conventions/` and complete skill directories under `skills/`, without a maintained resource catalog. Keep the hub's own operational skills under `.agents/skills/`.
- **BREAKING:** Replace convention AGENT-CARD comments with leading YAML frontmatter containing only a nonempty `trigger`; conventions are self-contained and may not declare requires or link to other conventions or skills. Use trigger text in the root AGENTS index and omit convention frontmatter from generated bodies. Preserve the H1/canonical filename contract; explicitly convert existing client cards through `apply --migrate` instead of silently rewriting authored sources.
- Keep SKILL.md standard frontmatter: optional string `metadata.requires` points to a skill-local `requires.yml` containing native YAML `conventions` and `skills` lists. No JSON-encoded YAML value, multiline encoded dependency value, root skill `requires` field, or per-dependency file is used. Copy and validate the dependency file with the complete skill tree.
- Only skills declare dependencies, with explicit string `id` and `source` (`local` or `hub`). Skills may depend on conventions and skills. Local skills may reference local or explicitly selected shared resources; shared skills may reference only their own hub/revision. Resolve local skills from project-owned sources and shared skills from accepted provenance, without implicit downloads or source fallback.
- Require all four convention-maintenance skills to enforce self-contained conventions: no requires declarations and no links to other conventions or skills. Each owns deterministic checks for convention/skill targets, including skill support files. Convention content that routes execution to a skill belongs in that skill; maintenance must route the refactor to the responsible authoring workflow. Skills retain their own description-based activation. AGENTS discovery links and identity-based skill dependency declarations remain valid; skill instructions may not directly link conventions or other skill trees.
- Require skill entrypoints/support instructions to mention external skills or conventions by identity instead of direct links or hardcoded cross-resource file paths. The agent discovers actual project resource locations from project instructions, skill discovery, and accepted id/source provenance. Keep links to a skill's own support files and path-free requires.yml declarations; mechanically reject cross-resource links during authoring, assembly, and import checks.
- Let an agentscli client optionally select resources from exactly one public or private Git remote, independently of hosting provider. Explicit selection is mandatory; dependencies must also be selected explicitly and never cause automatic downloads.
- Pin all selected resources to one exact hub commit, optionally resolved from a tag. Vendor only selected resource trees and their current integrity information under `.agentscli/hub/`, versioned with the project. Keep resource language literal and keep the main AGENTS template local.
- Add a client hub-management skill with included deterministic scripts for explicit acquisition, updates, selection changes, switching, and removal. Consumer apply and build-skill generation remain offline.
- Combine selected imported conventions in the ordinary generated index and materialize selected imported skills at the existing destination. Installed managed skill edits/extras are replaceable drift, not authored conflicts. Reject unmanaged collisions, reserved names, and invalid accepted source/state integrity before writes.
- Remove obsolete resources inside managed scopes, including edited installed hub skill trees on explicit deselection/detach. Preserve authored/state areas and unrelated paths. Preflight a complete replacement before switching hubs; missing selected candidate resources/dependencies fail before mutation.
- Record each imported file's content representation and Git executable mode. Compare UTF-8 text with canonical LF endings, preserve opaque payloads byte-for-byte, and restore installed text/mode drift offline without treating platform differences as authored edits. Retain executable metadata on Windows for later POSIX restoration.
- Establish a handwritten monorepo convention requiring deterministic mechanical validation wherever possible, and apply it to existing agentscli-only skills as well as hub skills. Put custom agent-operated validation scripts inside the skill that distributes them; keep semantic judgment in the instructions.
- Extend the language-only schema and three-skill distribution with optional hub configuration and a fourth client skill. Existing language-only configurations remain valid. Snapshot tampering remains invalid state; installed skill/document edits are discarded during managed replacement. Update upgrade guidance for apply and the explicit protected-path contract.

## Capabilities

### New Capabilities

- `hub-authoring`: Create/refresh a standalone hub through apply and validate/publish shared convention frontmatter and standard skills with skill-local YAML dependencies, preserving authorship/state.
- `hub-consumption`: Configure one optional Git hub, explicitly select and pin resources, vendor them locally, and perform deterministic updates and bounded cleanup through a skill.

### Modified Capabilities

- `agents-cli`: Expose apply only, reuse the skill-owned engine for managed replacement, and retain private offline script modes, previews, diagnostics, and JSON/exit semantics.
- `project-instruction-workflows`: Render trigger-based discovery, validate local/shared dependency origins, explicitly convert legacy cards, and preserve the existing authored/state and managed-replacement boundaries.
- `convention-authoring`: Separate administrative, consumer, hub-internal, and hub-shared authoring responsibilities, with exact names, targets, and context rejection.
- `skill-authoring`: Require 12 independent skill sources, deterministic checks, nine distributed provenance declarations, and standard metadata.requires references to complete requires.yml dependency files.
- `release-publication`: Deliver two independent workspace artifacts, establish the hub CLI's initial version/tag pattern, and release a new agentscli version after hub implementation with concrete candidate and remote verification.

## Impact

- Move current runtime, client assets, package-specific scripts, and unit tests into `packages/agentscli/`; add `packages/agentscli-hub/`. Root metadata becomes private orchestration with one lockfile. Keep handwritten instructions/conventions, the three independent administrative skills, OpenSpec, CI, and the Git hook at the root; packaged operational skills come only from their own package's assets.
- Reduce the public parser to apply and move the consumer generation engine into the build skill's own shipped support closure. Bootstrap uses that packaged engine and resources; build scripts operate only on project inputs. Extend configuration, rendering, assembly, and authoring guidance. Add a current-state lock/integrity record and injected Git boundary; no ownership history, recovery database, merge engine, or rollback service.
- Git and authentication are required only for explicit remote hub operations and hub Git initialization. Use native Git credentials and transport; no vendor SDK, token collection, custom login, server, or registry.
- Update workspace checks, build/pack preparation, README, root instructions/conventions, and internal release guidance. Preserve the existing Node lines and unit-only verification policy.
- Extend deterministic asset/frontmatter validation and archive inspection to verify all nine declared generators/versions against their owning package metadata, while preserving imported skill frontmatter and existing hub integrity semantics.
- Implementation includes the new hub package's first release and a new agentscli release after the hub is implemented, following native release guidance and immutable version/tag identities. This proposal invocation itself performs no implementation or delivery. Rollout to SGO or other unrelated client repositories is outside this change.
